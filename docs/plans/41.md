## Goal

Expose the mobile incident-list endpoint under `/mobile/v1` with the response shape and behavior shown in issue #41, without changing the existing internal API.

## Steps

1. Add the mobile list route and query behavior in `incidentdesk/api/mobile_incidents.py`, using the existing incident data and following issue #41's response example.
2. Add any mobile list request/response models in `incidentdesk/schemas.py`.
3. Register the router in `incidentdesk/app.py`.
4. Add focused endpoint tests in `tests/api/test_mobile_incidents.py`.
5. Add a plain-language entry under `## Unreleased` in `CHANGELOG.md`.

## Tests

- Verify the list endpoint's status code, response fields, and values match issue #41's response example.
- Verify supported query and pagination behavior and empty results as defined by issue #41.
- Run `scripts/test.sh tests/api/test_mobile_incidents.py`; it runs the selected tests in UTC and Asia/Singapore.

## Risks

- `incidentdesk/app.py`, `incidentdesk/schemas.py`, and `CHANGELOG.md` are also changed by sub-issues #42 and #43; coordinate these shared-file edits when integrating the parallel branches.
- This sub-issue does not depend on #42 or #43. The parallel implementations should use the same `/mobile/v1` API conventions and avoid changing the existing internal routes.

## Out of scope

- Incident detail and timeline behavior from #42.
- Alert subscriptions from #43.
- Changes to the existing internal incident API.
