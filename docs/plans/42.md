## Goal

Expose mobile incident detail and timeline endpoint(s) under `/mobile/v1` with the response shape and behavior shown in issue #42, without changing the existing internal API.

## Steps

1. In the owned file `incidentdesk/api/mobile_incident_detail.py`, add the mobile detail route and its response models, using the existing incident and timeline data and following issue #42's response example.
2. In the shared file `incidentdesk/app.py`, add `from incidentdesk.api import mobile_incident_detail` and `app.include_router(mobile_incident_detail.router)`.
3. In the owned file `tests/api/test_mobile_incident_detail.py`, add focused endpoint tests.
4. In the shared file `CHANGELOG.md`, add `- Mobile clients can view an incident and its timeline at \`/mobile/v1/incidents/{key}\`.` under `## Unreleased`.

## Tests

- Verify the detail response includes the incident and its timeline oldest-first, matching issue #42's example.
- Verify an unknown key returns 404 with `{"error": "not_found"}`.
- Run `scripts/test.sh tests/api/test_mobile_incident_detail.py`; it runs the selected tests in UTC and Asia/Singapore.

## Risks

- Owned files: `incidentdesk/api/mobile_incident_detail.py` and `tests/api/test_mobile_incident_detail.py`.
- Shared additions: the import and router-registration lines in `incidentdesk/app.py` above, plus the single Unreleased bullet in `CHANGELOG.md` above. Sub-issues #41 and #43 also add their own import/registration lines and one changelog bullet to those files; retain all three additions when integrating the branches.
- This sub-issue does not depend on #41 or #43. It shares no request or response models with them and can reuse existing incident and timeline data.

## Out of scope

- Incident list behavior from #41.
- Alert subscriptions from #43.
- Changes to the existing internal incident and timeline API.
